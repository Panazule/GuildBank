# Phase 5 Approval Review — Decision and Risk Package

**Status:** APPROVED by the owner on 2026-11-22 (plan reconciliation, second pass). This document is the review package that decision was based on and remains the record of rationale, tradeoffs and risk classification.
**Date:** 2026-11-22
**Companion plan:** `Docs/Phase5ImplementationPlan.md` rev 1.2 (normative). Where this review and the plan differ, the plan governs; this review adds the reasoning and the recommendations that the plan's tables do not carry.
**Scope of this package:** PD5-01–PD5-26 and PD5-28–PD5-30 (PD5-27, PD5-31 and PD5-32 were reviewed and approved in the first pass), plus R5-01–R5-16 and the four dispositions accepted as out of scope.
**Out of scope:** PD-05, PD-18, E-02 and the `AM-02` refresh/reconciliation residual. The owner accepted them as out of scope for Phase 5 (§16 of the plan); nothing below reopens them.

**How to read this document**

- **Rationale** — why the decision is the one the plan needs, in one paragraph.
- **Primary tradeoffs** — what the decision costs, and the alternative that was rejected.
- **Impact on later phases** — what a later phase inherits, can reuse, or must not contradict.
- **Recommendation** — the reviewer's position, with the condition that would change it.

No code is proposed here. Every statement is about behavior, contracts, data or operations.

## 1. Decision review (PD5-01–PD5-26, PD5-28–PD5-30)

| ID | Decision, in one line | Rationale | Primary tradeoffs | Impact on later phases | Recommendation |
|---|---|---|---|---|---|
| PD5-01 | Persist `LocationGroup`/`LocationSort` on `GuildBankItems` in migration `0003`; `SourceLocation` stays the raw user-visible value | D-05 requires filtering and grouping by location, and the public list already sorts by name; normalizing inside a query would mean a full scan on every page and a second copy of the rules in SQL. Persisting the derived pair keeps one normalization implementation (in Go), makes the grouping indexable, and leaves `SourceLocation` untouched so no display or audit value changes. Nullable columns let the backfill be restartable and let the migration be applied before the data pass. | Two extra columns (~144 bytes plus index) on a table that import writes in 500-row chunks, and a mandatory backfill window during which the columns are partially null. The rejected alternative — deriving on read — avoids schema change but cannot use an index and drifts from import's staged values. | Every later admin, reporting or export feature that groups or filters by location reads these columns instead of re-deriving. If a later phase changes D-05 rules it must backfill again; the columns are not self-healing. Public DTOs are unaffected. | Approve. Revisit only if a future phase introduces a location dimension that `LocationGroup`/`LocationSort` cannot express. |
| PD5-02 | Idempotent startup backfill after migrations, before the HTTP listener: keyset batches of 500, advisory lock, one transaction per batch, progress every 10,000 rows, fail startup on error | Derived fields must never be observed half-populated, because a page sorted by location would silently misorder rows. Running before the listener removes the race with both requests and import commits, and a keyset walk with a null predicate is naturally resumable, so a crash mid-run costs only the current batch. The dedicated lock stops two replicas from duplicating work and keeps the global mutation lock semantics intact. | Startup latency on a large table (R5-02) and a hard failure mode: a bug aborts boot rather than opening a degraded site. The alternatives — lazy per-row normalization or an offline script — either spread the work into request latency or need an operator step that can be forgotten. | Later migrations that add derived columns can copy this pattern; later phases inherit a schema where derived columns are guaranteed populated before serving. Operators inherit a restart-to-resume behavior that must stay documented in the runbook. | Approve. If a future dataset makes boot time unacceptable, convert to an opt-in maintenance mode rather than weakening the "no half-populated reads" rule. |
| PD5-03 | One `normalizeLocationValue` core behind two wrappers: `NormalizeLocation` (import contract, unchanged) and `NormalizeAdminLocation` (same group/sort plus `location_unrecognized` warning when a non-blank value falls to `Unspecified`) | `Design.md` D-05 and AM-04 define a closed set of canonical groups, and import already implements exactly those rules; inventing a general title-caser would create groups the spec does not have ("The Bazaar", "Pok"). Two wrappers over one core keep import behavior frozen (its warnings are asserted by Phase 3 tests) while giving the admin a visible signal that a raw value was kept but not grouped. The warning is the difference between an administrator trusting a wrong group and correcting the raw text. | Two entry points over one implementation, so a future rule change has to be made once in the core and consciously in both wrapper contracts. Admin accepts a malformed value as `Unspecified` rather than rejecting it; the rejected alternative is a hard `422`, which would block legitimate but unconventional location text. | Future import, public filtering and any export share the same group vocabulary. A later phase that adds locations (new bank tabs, new housing zones) must extend the core, not fork it, and must decide whether the admin warning stays. | Approve. Require that any future D-05 change lands in `import_normalize.go` and updates the admin wrapper's warning contract in the same change. |
| PD5-04 | JSON writes reuse the public resource paths (`POST/PUT/DELETE /api/v1/items…`, `/restore`) with method-level admin authorization; admin reads live under `/api/v1/admin/…`; audit under `/api/v1/audit` | `Docs/ImplementationPlan.md` §4 and D-03 already name the item paths for mutation, so reusing them keeps one URL vocabulary for the resource instead of inventing `/admin/api/…`. Authorization is applied per method, which is the smallest change that cannot be bypassed by a proxy or a forgotten route group. Admin reads use separate routes because a representation that changes shape by authentication state is exactly what E-07 and PD4 forbid: public clients must not be able to infer an "extra fields" variant exists. | The public `GET /api/v1/items` and the admin `GET /api/v1/admin/items` describe the same rows differently, so two serializers and two test suites must stay in step. The alternative — one route with conditional fields — is cheaper to write and materially worse to test and to reason about. | Every later phase that adds admin mutations can reuse the pattern (public path, admin authorization), and the public contract stays frozen. Two read shapes also mean two places to update when a column is added, which the DTO allowlist tests in §13 make visible. | Approve. Conditions: no method on `/api/v1/items` may be admin-only without an explicit test, and no admin field may appear in a public response. |
| PD5-05 | HTML routes under `/admin/…` with thin POST adapters that enforce admin/CSRF, call the same service method, and redirect `303` with a fixed notice code | The specification places the admin screen in the authenticated admin area, and full-page forms are the only way to satisfy the no-JavaScript constraint. Adapters that translate form fields to the same service input keep one set of business rules, and fixed notice codes avoid echoing user text into a redirect URL (open-redirect and reflected-content class of bugs). The API stays the canonical machine contract rather than the UI growing its own. | An extra request per action (post–redirect–get) and a second input mapping to maintain next to JSON decoding. The rejected alternative — HTMX or fetch-based forms — removes the round trip but violates the no-JS rule and adds client state the tests cannot cover. | Later phases that add admin surfaces inherit the route naming, the notice-code vocabulary and the adapter pattern; they do not need to re-derive CSRF or authorization. Any future SPA-style UI would have to keep the adapters as the only writers. | Approve. Conditions: notice codes are an enum, never free text, and the redirect target is always a server-chosen path. |
| PD5-06 | A manual add is one atomic operation for one EQUID and one quantity; the server derives identity, decoded strings, `NameSort`, `DateAdded`, both lifecycle dates, `ModAt`, actor fields and both location fields | This mirrors Phase 3 import commit, which already resolves metadata, normalizes location and derives dates from one clock; a second, browser-driven derivation would drift on day one. One EQUID and one quantity per request keeps the transaction small, makes the audit row unambiguous and lets the response report which IDs were created. Deriving `DateAdded` server-side is what makes "date entered this guild bank" true regardless of client clock or timezone. | The client cannot set identity fields even when correcting bad data, so a wrong name requires metadata resolution or remove-and-re-add (PD5-10). Multi-EQUID entry becomes N requests, which is also what makes PD5-28's lack of idempotency visible. The rejected alternative — a batch create endpoint — multiplies partial-failure semantics and audit shapes for a case the UI does not present. | Later phases that import or migrate data should reuse the shared insert helper rather than write a third column list. Any future bulk entry needs its own decision precisely because PD5-06 deliberately does not provide it. | Approve. Condition: the shared helper is exercised by both import and admin tests so a column-list drift fails a test rather than production. |
| PD5-07 | Quantity caps: ordinary item `1..100,000` (row per unit), spell `1..4,294,967,295`, update `1` for items and the spell ceiling for spells; `existing + added` overflow rejected before update | Ordinary items are stored one row per unit, so the only thing standing between a typo and a hundred million inserts is a server-side cap; the database ceiling (`INT UNSIGNED`) is meaningless as a guard there. A spell's quantity is a single column, so its natural bound is the column type, and any lower cap would be an invented business rule. Rejecting zero forces removal/restore to be the only way to reach zero, which keeps audit meaningful. | 100,000 is a judgement value: it is large enough for a real guild-bank stock and small enough to bound a request, but it is not derived from the spec and could need adjustment. The rejected alternative — no cap below the column type — risks a self-inflicted denial of service through one form field. | Later phases that add bulk operations must respect the same expansion cost; a future import UI that reuses this endpoint inherits the cap. The cap constant should live in one place so a later owner decision changes it once. | Approve, and record 100,000 as a revisit-if-measured constant rather than a specification fact. |
| PD5-08 | Adding a spell merges into the lowest-ID active spell row for that EQUID, preserving its location, recipient and dates; duplicates produce a `duplicate_spell_target` warning and the lowest ID wins | Phase 3 commit already merges spell stacks (D-09), and a manual add that created a second active spell row would give the public read path two candidates for the same thing. Preserving the target's location and recipient avoids silently moving stock as a side effect of adding quantity. Choosing the lowest ID makes the outcome deterministic and reproducible, and the warning surfaces legacy duplicates without a destructive automatic cleanup. | A merge can never carry a new location, a new recipient or a date override, which is why PD5-27/PD5-32 reject those inputs with `422` instead of dropping them. Legacy duplicate rows persist until someone edits or removes them. The rejected alternative — consolidate duplicates automatically — is a data migration disguised as a create. | Any later reconciliation feature inherits the duplicate problem as data, not as behavior. Reports that count spell rows rather than summing quantity will disagree with the merged view until duplicates are dealt with. | Approve. Condition: the merge target is chosen by a documented deterministic rule and its ID is returned in the response. |
| PD5-09 | Missing metadata requires a fallback name; blank/whitespace returns `422 field=name`; otherwise store the trimmed name, blank class/race, `MetadataMissingFg=1` and a `metadata_missing` warning; a submitted name is ignored when metadata exists | AM-01/AM-02 and D-08 require that an item with no metadata still be representable without inventing a sentinel. A required fallback name makes the administrator supply the only human-meaningful identifier available, while the flag keeps the row honest about what is known. Ignoring a submitted name when metadata exists prevents a field that looks editable from having no effect, and the warning explains the blank class/race. | A missing-metadata row is permanently lower quality until the AM-02 refresh residual is solved (accepted out of scope), and the admin must type a name by hand for each such EQUID. The rejected alternative — blocking creation until metadata exists — makes the guild bank unusable for items the upstream `Items` table does not know. | The flag and fallback name are the contract later reconciliation work will consume; any future refresh must decide what to do with a hand-typed name. Public filtering already treats these rows as a distinct state, so later phases must not "fix" them by guessing. | Approve. Condition: the flag is set by the server only, never by the client, and the warning is non-fatal. |
| PD5-10 | Identity and lifecycle fields are immutable through update: `EQUID`, `ItemType`, `Name`, class/race, `NameSort`, `MetadataMissingFg`, `DateAdded`; editable fields are quantity (spells), source location, recipient and the two later dates; immutable fields present in the body are `422` | D-06/D-07 make identity date-bound: changing the name or EQUID of a stored row would invalidate the audit trail, the public filter results and any downstream reference, so the only honest correction is remove plus re-add. Rejecting rather than ignoring an immutable field in the body prevents a client from believing it succeeded. Spelling out the editable set is what made the PD5-32 date editing possible without reopening identity. | Correction of a misidentified row costs two operations and a new `DateAdded`, which is visible in history. The rejected alternative — silent ignore — is cheaper for the server and actively misleading for clients. | Later phases that accept row edits inherit the same list; anything that wants to "repair" a name is a data-migration concern, not an update. The immutability of `DateAdded` is what keeps import and admin semantics identical. | Approve. Condition: the immutable set is asserted by one shared table-driven test used by both the decoder and the service. |
| PD5-11 | Optimistic concurrency via `expectedModAt` from the admin read (body for `PUT`, query/hidden field for `DELETE`/`restore`), microsecond comparison under a row lock, `409` on mismatch, new `modAt` returned | Two administrators editing one row is the realistic failure mode in a shared guild bank, and last-write-wins would silently destroy the other edit. `ModAt` already exists as `DATETIME(6)` and is already updated by every write, so using it needs no schema change and no ETag framework. Microsecond equality matches the column precision, and a generic conflict message avoids leaking the other user's values. | Clients must carry a token they did not choose, and a stale tab always fails rather than merging. Clock skew is irrelevant because the value is compared, never computed. The rejected alternative — `If-Match`/ETag — is more idiomatic HTTP but needs representation hashing and does not help the no-JS forms. | Later phases that write these rows must send `expectedModAt` too, or they bypass the protection entirely. Any future bulk editor needs a per-row token, not one token for a page. | Approve. Condition: every admin write path, including restore, is covered by a conflict test. |
| PD5-12 | Removal is a reversible soft delete: `DELETE` sets `DeletedFg=1` plus attribution and writes `ITEM_REMOVED`; `restore` clears the flag, updates attribution and writes `ITEM_UPDATED` with note `restored`; wrong state is `409`, missing is `404` | D-04/AM-03 treat removal as a state change rather than deletion, and the public read path already filters on `DeletedFg`, so a soft delete keeps the audit trail, the ID space and any external references intact. Explicit `409` on an already-removed or already-active row is what makes the audit meaningful: a no-op "success" would log a change that did not happen. No hard-delete path is exposed at all, so the only way to lose a row is a deliberate database operation outside the application. | Rows accumulate forever and every query must carry the `DeletedFg` predicate, which the Phase 5 indexes all do. Restoring an old row brings back its original dates, which may now be long past — accepted, because rewriting them would break AC5-19. The rejected alternative — hard delete with an audit copy — destroys the ability to restore. | Later retention or purge work inherits a table that only grows; any future archive job must respect the same filter and the audit trail. Restored rows keep their original IDs, so inbound references never break. | Approve. Conditions: the restore path is audited, and no route, service method or SQL grants a hard delete. |
| PD5-13 | All admin writes take the existing import-commit advisory lock on a dedicated connection, open a transaction, lock rows with `SELECT … FOR UPDATE`, write inventory plus exactly one audit row, then commit; deadlock retried once with the same captured `now`; lock timeout is `503` | Import commit and manual edits touch the same rows and would deadlock or race without a shared lock; reusing the existing global lock means one serialization scheme rather than two that can interact badly. Doing the audit insert inside the same transaction is the only way to guarantee "no mutation without history", which is an acceptance criterion. A dedicated connection is required because `GET_LOCK` is connection-scoped and a pooled connection would release the lock at an unpredictable time. | Manual writes queue behind a large import commit, and an admin write briefly blocks imports (R5-05/R5-11). Retrying once with the captured timestamp keeps `DateAdded`/`ModAt` consistent across the retry. The rejected alternative — per-row locking only — leaves the merge-target and duplicate-spell decisions unprotected. | Later phases that mutate `GuildBankItems` must take the same lock or accept deadlocks with import. Any future background job writing these rows inherits the same rule. Retry and timeout behavior should stay in one helper so it is not re-implemented. | Approve. Condition: the lock is always released via `defer` on every error path, including panics, and a test proves no lock leak. |
| PD5-14 | Audit event codes are `ITEM_CREATED`, `ITEM_UPDATED`, `ITEM_REMOVED` with `TableName='GuildBankItems'` and `RecordID` as the decimal primary key; merge and restore use `ITEM_UPDATED`; `Notes` holds only fixed machine text or NULL | A small closed vocabulary is what makes the audit viewer filterable and what lets later phases assert behavior; matching the ImplementationPlan vocabulary avoids a second naming scheme. Decimal `RecordID` is the same convention the existing `insertAudit` uses. Restricting `Notes` to fixed text keeps user input in the structured fields where it is escaped and typed, instead of in a free-text column rendered in a table. | Merge and restore are not separately distinguishable by event code, so consumers must read the note or the changed fields to tell them apart. The rejected alternative — one event code per variant — multiplies filters for events that are semantically the same row change. | The audit viewer, any later export and any future compliance query depend on this vocabulary staying stable. New events in later phases must be added to the same closed set, not invented locally. | Approve. Condition: event codes are declared once as typed constants shared by service, API filters and templates. |
| PD5-15 | Audit old/new JSON is an explicit allowlist written by the service: create carries `equid`, `itemType`, `name`, `quantity`, `sourceLocation`, `givenTo`, `metadataMissing`, `createdIds` (first 100 plus count); update/restore carries only changed fields plus new `quantity`; remove carries `{deletedFg:true}` | Audit is the evidence trail, so it must record what changed without becoming a copy of the request. An allowlist keeps bearer tokens, session material, headers and SQL out of a JSON column that the viewer renders, and bounding `createdIds` prevents a 100,000-row add from duplicating the whole response into one row. Recording only changed fields on update makes the audit readable and keeps the row small. | An allowlist has to be maintained: a new column is invisible to audit until someone adds it, and a mistake omits evidence. The rejected alternative — dump the whole request — is simpler and leaks and bloats. | Later phases adding columns must decide explicitly whether they are audited; this is a small recurring cost that keeps audit JSON bounded (R5-10). Any future audit export inherits these shapes. | Approve. Condition: the allowlist lives next to the write code so a reviewer sees both in one diff. |
| PD5-16 | Admin-only audit viewer, newest-first, offset paginated, filtered by `eventType`, `user`, `table`, `recordId`, `correlationId`, `from`, `to` (inclusive UTC dates, `to` becomes `< next day`); page size 50 default, max 200, page max 10,000; the per-record history panel reuses the same read path | E-09 wants operational evidence, and the cheapest credible implementation is a filtered read over a table that already exists rather than a generic audit platform. Exact-value filters keep the query indexable and predictable; date bounds as inclusive UTC days match how administrators think about "yesterday" and avoid a bare timestamp comparison. Reusing the one read path for the per-record panel means the panel cannot show something the viewer cannot. | Offset pagination on a large audit table degrades for deep pages, which the page cap bounds rather than solves; newest-first with filters also means no free-text search, so finding an actor by partial name is not possible. The rejected alternative — keyset pagination — is better on deep pages but conflicts with a page-number UI. | Later phases that add audit events must keep the filter vocabulary closed, and any future export or retention job reads the same table. If audit volume grows, the page cap and offset model are the first things to revisit. | Approve. Condition: `from`/`to` parsing is validated as strict `YYYY-MM-DD` and the end bound is exclusive of the next day. |

An allowlist for sorts is the only safe way to build an `ORDER BY` from a query parameter, and treating an unknown enum as `422` rather than silently defaulting tells a client its request was wrong. Empty results as `200` keeps pagination arithmetic intact for clients. | Deep pages and large page sizes cost queries on 1M rows (R5-03/R5-04), bounded by the caps rather than eliminated. Rejecting unknown enum values is stricter than many clients expect, and the rejected alternative — coerce to default — hides typos. | Later admin or reporting screens should reuse the same list contract rather than adding a second pagination dialect. Any future full-text search replaces the `LIKE` path (R5-03) behind this same contract. | Approve. | PD5-18 | Strict JSON decoding: `MaxBytesReader` 64 KiB, token pre-pass rejecting duplicate keys, `DisallowUnknownFields`, single-value check, `Content-Type: application/json`; `400` for shape errors, `413` for oversize; Gin form binding only in HTML adapters | No existing handler establishes the whole contract — the selection PUT lacks duplicate-key and trailing-value checks and settings uses `ShouldBindJSON` — so Phase 5 has to choose, and the strict option is the only one consistent with "immutable fields are rejected". ## 2. Risk review (R5-01–R5-16)

Every risk is assigned exactly one **primary class**, because that determines who owns the remaining exposure:

- **Acceptance** — the behavior is a deliberate limit of the approved design. The mitigation is documentation and measurement, not code. The owner accepts the residual by approving the plan.
- **Implementation-time mitigation** — the risk is real but closed by a specific, testable piece of the work. It is an acceptance criterion, not a hope.
- **Operational** — the risk lives in deployment, scheduling or environment and no code change removes it. It needs a runbook line or a granted database privilege.
